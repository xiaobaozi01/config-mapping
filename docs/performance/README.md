# 配置适配性能改造与复测说明

日期：2026-11-02。环境：macOS arm64、Python 3.12.13。
所有输入均为合成配置或仓库公开测试样例，没有读取真实项目配置。
基线源码为 `caf31a1`；接口匹配阶段为 `f1a031e`；性能采样的运行时代码为 `d8cbc72`，随后 `d1b658b` 补充未追踪节点协议兼容，不改变 AST 事务机制。

## 改动与收益来源

1. 接口引用检查不再每处理一行都重建接口字典。上下文持有名称索引，文档持有上限 32,768 条的候选提取缓存；名称集合与候选提取分离。
2. 节点字段和完整普通列表写操作进入变更日志。规则各回调阶段禁止写入，包含通过另一个 Editor 提交；查询缓存使用即时变更序号，包含开放 bulk 内的直接写入。
3. 规则进入作用域只记录日志检查点。成功规则不为回滚复制整树，也不计算全树签名；嵌套同步只处理新增日志。父关系索引只更新受影响的边和子树。
4. 回滚逆序撤销日志，并在失败路径复制恢复后的树，以保留旧引用失效保证。独立嵌套回滚的根替换继续纳入外层日志。
5. 裁剪使用共享祖先路径栈，命中引用时才构造完整路径，保留源码顺序和整节点删除后的跳过行为。`nodes` 元组接口保持不变，内部 walk 减少中间元组。
6. 子列表使用 slots；唯一父关系使用紧凑元组，多父关系才临时使用字典。断开的子树不积累在索引中，节点弱引用追踪器，保留节点不会滞留 Document 和解析缓存。

完整签名仍可显式用于诊断。新树安装、解析片段和业务本身要求的子树复制不属于被取消的冗余操作。
节点追踪和事务修改是一个原子改造：无法在继续允许 bulk 直接修改的同时，仅给 Editor 加 dirty 标记并安全删除全树检查。

## 测量方法与结果

时间测试不启用 cProfile 或 tracemalloc，先预热一次，再取三次中位数。调用计数和内存峰值分别在额外运行中采集；输入解析不计入规则执行时间。构造开销另测。
小规模 2,300 节点实验只作参数与一致性烟测，使用一次计时，不用于稳定性能结论。扩展实验使用约 46,000 节点、40 条规则、每批 200 次字段修改。

### 约 23,000 节点、20 条规则的机制基准

| 场景 | Cisco 修改前 → 修改后 | Juniper 修改前 → 修改后 |
|---|---:|---:|
| 只读规则 | 6.139 s → 0.232 ms | 6.297 s → 0.224 ms |
| 无修改规则 | 6.147 s → 0.241 ms | 7.022 s → 0.246 ms |
| 每规则修改一个 header | 7.098 s → 0.377 ms | 7.077 s → 0.873 ms |
| 每批修改 100 个节点字段 | 2.147 s → 27.291 ms | 2.213 s → 10.047 ms |
| 连续 20 次失败回滚 | 2.168 s → 2.543 s | 2.063 s → 3.043 s |

这些规则刻意只选择一个叶节点，用来隔离规则框架对整树的固定开销。它们没有执行真实项目的完整业务遍历，因此这里的大倍率不能解释为整体映射加速。

结构计数更有代表性：

- 20 条只读规则：整树回滚 clone 20 → 0，tree_signature 160 → 0，bind_parents 20 → 0。
- 20 条稀疏修改规则：整树回滚 clone 20 → 0，tree_signature 180 → 0。
- Juniper 稀疏修改仍有 20 次 bind_parents，来自每次 header 校验解析的独立两节点片段，并非重绑当前文档。专项测试禁止对当前文档根调用该重绑。
- 46,000 节点、40 条只读／无修改规则仍无全树签名、克隆或重绑，耗时约 0.4～0.5 ms；成本不再随未选中树的节点数放大。

接口引用实验处理 2,000 行、100 个名称、10 种重复 header：约 24.843 ms → 0.930 ms，约 26.7 倍；规范化调用 4,000 → 10。单独在接口匹配阶段的历史版本上运行得到约 0.896 ms，验证该收益不依赖后续 AST 改造。

### 完整裁剪流程的样例差分

`pruning_differential.py` 对 19 份样例分别运行保护和不保护接口两种情形，共 38 组：

- 20 组 Cisco：加速中位数约 2.23 倍，范围约 1.50～2.95 倍。
- 18 组 Juniper：加速中位数约 1.37 倍，范围约 1.15～1.68 倍。
- 所有组的配置文本、部署渲染、完整 AST 签名、接口查询及业务报告摘要一致。

原实现部分 BGP 审计／诊断的顶层事件顺序受对象身份集合枚举影响，在相同版本多次执行间就会变化。差分脚本仅规范化报告顶层 changes、warnings、errors 的顺序，保留事件重复次数、嵌套路径和载荷顺序。另有固定随机种子的裁剪遍历测试直接比较事件顺序，验证显式栈没有改变遍历顺序。

这些样例较小，单次为亚毫秒到数毫秒，测量受环境噪声影响。真实项目收益仍需在公司环境确认。

### 代价与限制

| 构造约 23,000 节点文档 | Cisco 修改前 → 修改后 | Juniper 修改前 → 修改后 |
|---|---:|---:|
| 构造及合成输入准备时间 | 0.103 s → 0.305 s | 0.206 s → 0.374 s |
| 构造后保留内存 | 11.00 MiB → 16.08 MiB | 11.37 MiB → 16.47 MiB |
| 构造峰值分配 | 14.17 MiB → 22.40 MiB | 14.60 MiB → 22.92 MiB |

增量归属索引增加约 5.1 MiB／文档的常驻开销，并把一部分成本移到首次安装。构造测量包含合成输入和基准上下文准备，与规则计时分离。

连续失败回滚的极端实验仍有回退：Cisco 时间增加约 17%，Juniper 约 48%；操作期间峰值分配约 25.9／26.0 MiB → 44.6／44.3 MiB。原因是恢复后的独立树还需要重新建立索引，并保留旧引用失效语义。实现已消除重复索引和校验遍历，但没有通过放宽回滚保证规避该成本。

因此本改造适合反复在同一文档上执行多条成功规则；频繁解析后只执行一次操作，或大量规则失败的任务，必须同时评估构造及回滚代价。规则阶段的 peak_mib 从构造后开始追踪，不包含文档已有常驻内存，不能与构造峰值混为一谈。内存数据为 Python 分配追踪，不是进程 RSS。

## 本地复现

从项目根目录运行，使用同一个 Python 环境、同一机器和相同参数，计时实验避免同时运行其他重负载任务：

```sh
PYTHONPATH=src .venv/bin/python benchmarks/mapping_hotpaths.py --nodes 23000 --rules 20 --edits 100 --repeat 3 > result.jsonl
PYTHONPATH=src .venv/bin/python benchmarks/mapping_hotpaths.py --construction > construction.jsonl
PYTHONPATH=src .venv/bin/python benchmarks/pruning_differential.py --repeat 3 > pruning.jsonl
.venv/bin/python benchmarks/compare_results.py before.jsonl after.jsonl
```

比较不同版本时，使用当前同一份基准脚本，仅将 PYTHONPATH 指向对应版本的 src。脚本保留旧版兼容入口，可用于改造前的源码。运行构造基准时输出格式不同，不传给 compare_results.py。

已保存原始 JSONL：`baseline`／`optimized` 为主实验，`interface-stage` 为接口匹配阶段，`construction-*` 为构造开销，`pruning-*` 为完整裁剪，`small-*`／`scaled` 为规模检查。`rollback-final` 为单次索引重建改进后的失败路径复测，该两行已更新进入 optimized 主结果。

## 公司内复测与验收

真实配置只留在公司环境。旧版与新版使用相同解释器、依赖、规则、输入及运行入口，分别执行：

1. 不开 profiler，记录完整映射及解析、接口处理、裁剪、校验、输出各阶段时间；独立重复三次以上，报告中位数。
2. 单独运行 cProfile，返回指定函数的聚合调用次数及自身／累计时间，不相加解释累计时间。重点关注 tree_signature、clone、bind_parents、interface_references，以及真正业务遍历的新热点。
3. 单独测量进程峰值 RSS 或 Python 峰值分配，注明测量口径，区分文档构造与执行阶段；分别统计规则成功数和失败回滚数。
4. 在内部比较配置输出和业务报告。若事件已有非确定顺序，明确比较规则，不直接忽略差异。

对外只需提供版本、设备／节点／规则规模、聚合时间与内存、热点计数、成功／回滚次数、结果一致性结论。无需发送原始配置、接口标识、路径内容或业务报告文本。
